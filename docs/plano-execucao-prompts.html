Como usar este playbook

  1. Cole primeiro as “Regras Globais” (abaixo) no início de cada sessão do Claude Code, ou salve-as em CLAUDE.md na raiz do repositório para que valham automaticamente em toda sessão.
  2. Execute a Onda 0 antes de qualquer outra coisa. Ela cria a rede de segurança (staging, backups, CI, proteção de branch). Sem ela, corrigir segurança em produção é arriscado.
  3. Siga as ondas em ordem. A sequência foi desenhada por dependência e risco: cada onda pressupõe a anterior concluída e verificada. Não pule para “ligar pagamentos” antes de fechar segurança e resolver o webhook.
  4. Um prompt = um PR. Cada prompt produz uma branch e um Pull Request pequeno e revisável. Só faça merge com CI verde e preview validado.
  5. Cada prompt já pede verificação e plano de rollback. Não considere “pronto” sem os critérios de aceite atendidos.

# Regras de Engenharia — Ervatório

## Fluxo de trabalho (obrigatório)
- Nunca commite direto na `main`. Sempre crie branch `feat|fix|chore/` e abra PR (draft).
- Um PR = uma mudança pequena e revisável. Não misture temas.
- Só faça merge com: CI verde, preview Vercel validado e critérios de aceite atendidos.
- Toda mudança de risco vai atrás de feature flag (padrão: desligada em prod).
- Todo PR descreve: objetivo, o que muda, como testar, e plano de rollback.

## Segurança de dados (Supabase / Postgres)
- Toda tabela nova nasce com RLS habilitado. Sem exceção.
- Toda policy de `UPDATE`/`INSERT` tem `WITH CHECK` explícito. Nunca deixe colunas de privilégio (`is_admin`, `role`) editáveis pelo próprio usuário.
- Views que expõem dados de usuário usam `WITH (security_invoker = true)` ou não são concedidas a `authenticated`/`anon`.
- Operações que exigem `service_role`, recálculo de preço, ou integração externa vão para Edge Function — nunca para o cliente.
- Autorização (admin vs. usuário) é validada no servidor (Edge Function/RLS), nunca só no JavaScript do cliente.

## Segredos
- Nunca coloque `service_role`, tokens de API ou secrets em arquivos servidos ao navegador, no HTML, ou no repositório.
- Segredos vivem em Supabase Secrets / Vercel Environment Variables. A única chave pública aceitável é a `sb_publishable_...`.
- Antes de commitar, rode varredura de segredos (gitleaks/trufflehog).

## Migrations
- Toda mudança de schema é uma migration versionada e idempotente (`IF NOT EXISTS`, `CREATE OR REPLACE`).
- Teste a migration em um Supabase branch (staging) antes de aplicar em produção.
- Migrations nunca destroem dados sem backup verificado e passo de rollback documentado.

## Pagamentos (Mercado Pago)
- O total do pedido é sempre recalculado no servidor a partir do preço autoritativo do banco. Nunca confie em valor vindo do cliente.
- Toda mudança no fluxo de pagamento é testada em sandbox ponta-a-ponta antes de ir a produção.
- Não ligue pagamentos em produção enquanto a validação de assinatura do webhook não estiver funcionando ou uma decisão de risco documentada for tomada.

## Compliance
- Nenhum script de tracking (analytics, pixel) dispara antes do consentimento do usuário (LGPD / Consent Mode v2).
- Dados pessoais têm base legal, política de retenção e caminho de exclusão.

Regra da onda

Cada migration é aplicada primeiro no branch de staging, validada com uma conta de teste tentando o abuso, e só então promovida. Nada de service_role no cliente.

1.1 — C-1 · Fechar escalonamento de privilégio (is_admin)

P0 · CríticoDepende: 0.1
Objetivo: impedir que um usuário altere o próprio is_admin/role via PostgREST.
Contexto: a policy de UPDATE de `public.user_profiles` (ervaria-supabase-migration.sql:98) usa apenas `USING (auth.uid()=id)`, sem WITH CHECK. Como `is_admin` (ervaria-admin-migration.sql:10) e `role` vivem nessa tabela, qualquer usuário logado pode executar via a chave publishable: `update user_profiles set is_admin=true where id=auth.uid()`. Isso é escalonamento a admin. Siga CLAUDE.md.

Tarefa: crie a migration supabase/migrations/<timestamp>_fix_user_profiles_privilege.sql que:
1. Faça DROP da policy de UPDATE atual e recrie com `WITH CHECK` garantindo que `is_admin` e `role` não podem ser alterados pelo próprio usuário (compare com o valor atual via subquery, ou melhor: revogue UPDATE nessas colunas e conceda UPDATE apenas nas colunas seguras — display_name, avatar_url, preferências).
2. Documente que a promoção a admin passa a ser feita apenas via SQL com service_role / Edge Function.
3. Seja idempotente.

Critérios de aceite: com uma conta comum autenticada, um UPDATE tentando setar `is_admin=true` é rejeitado pelo RLS; um UPDATE em display_name continua funcionando.
Verificação: escreva um teste (script SQL ou snippet supabase-js) que prove os dois casos no branch de staging. Mostre a saída.
Rollback: migration reversa que restaura a policy anterior (documentar, mas NÃO aplicar salvo emergência).

1.2 — C-2 · Fechar vazamento de PII na view de pedidos

P0 · CríticoDepende: 1.1
Objetivo: impedir que qualquer usuário autenticado leia pedidos/e-mails/endereços de todos os clientes.
Contexto: a view `public.orders_with_items` (ervaria-orders-migration.sql:258) NÃO é `security_invoker`, então roda com privilégio do dono e ignora o RLS das tabelas subjacentes. Ela é consumida pelo cliente autenticado em js/admin-orders.js:17, o que prova exposição via PostgREST. Qualquer usuário logado lê todos os pedidos, totais, endereços, nomes e e-mails. Siga CLAUDE.md.

Tarefa: crie a migration <timestamp>_secure_orders_view.sql que:
1. Recrie a view com `WITH (security_invoker = true)` (assim o RLS de orders/user_profiles é aplicado ao chamador); OU, se a listagem admin precisa cruzar dados de vários usuários, `REVOKE SELECT ON public.orders_with_items FROM anon, authenticated` e crie/uso uma Edge Function `admin-orders` (service_role) que valida `caller.isAdmin` e retorna a listagem — atualizando js/admin-orders.js para chamar a function em vez da view.
2. Garanta que o portão admin é feito no servidor, não só no cliente.

Critérios de aceite: uma conta comum autenticada recebe 0 linhas (ou 403) ao consultar dados de outros usuários; o admin continua vendo a listagem.
Verificação: teste com conta comum e conta admin no staging; mostre as duas saídas.
Rollback: documentar a view anterior; reverter o PR se quebrar o painel admin.

1.4 — Resolver assinatura HMAC do webhook + remover tabela de debug

P0Bloqueia pagamentosDepende: 0.2
Objetivo: validar a assinatura do webhook Mercado Pago de verdade (pré-requisito para ligar pagamentos com segurança) e remover o scaffolding de debug. (Backlog #17, #18.)
Contexto: leia WEBHOOK_SIGNATURE_DEBT.md. O HMAC computado em supabase/functions/_shared/mercadopago.ts nunca bate com o `v1` do header `x-signature`; hoje roda em "modo relaxado". Hipótese principal não testada: o MP assina o body bruto byte-a-byte, mas o código reconstrói a partir do JSON parseado. A tabela `mp_webhook_log` grava headers/body de requisições NÃO autenticadas (write-amplification). Siga CLAUDE.md.

Tarefa:
1. Em mp-webhook/index.ts, clone a request e capture `await clone.text()` (body_raw) ANTES de parsear.
2. Reproduza o HMAC-SHA256 conforme o formato documentado do MP (`id:;request-id:;ts:;`), testando também: body_raw exato, com/sem trailing newline, secret como string UTF-8 e como bytes hex-decodados. Registre qual variante bate.
3. Quando encontrar, remova o modo relaxado e faça a função retornar 401 em assinatura inválida (test e prod).
4. Remova a tabela de debug `mp_webhook_log` e todo o logging de dados não autenticados (ou restrinja a um log mínimo sem PII, com retenção).
5. Mantenha as defesas existentes (re-fetch do pagamento na API MP, checagem de external_reference e de valor, idempotência).

Critérios de aceite: webhook com assinatura válida → 200; assinatura inválida → 401; simulação do painel MP valida; nenhum insert de body bruto de request não autenticada.
Verificação: teste com a ferramenta "Simular notificação" do MP em sandbox; mostre logs.
Rollback: feature-flag para reativar modo relaxado em emergência, documentado.

1.5 — Headers de segurança, CORS restrito e rate limiting

P1Depende: 0.1
Objetivo: endurecer a borda. (Backlog #67, #68, #69, #70.)
Contexto: não há headers de segurança (sem vercel.json). CORS das Edge Functions é wildcard `*` (_shared/cors.ts:5). Não há rate limit. Siga CLAUDE.md.

Tarefa:
1. Crie vercel.json com headers de segurança: Content-Security-Policy (permitindo Supabase, Google Fonts se ainda usadas, e o que o app precisa — comece em Report-Only para não quebrar), Strict-Transport-Security, X-Frame-Options: DENY, X-Content-Type-Options: nosniff, Referrer-Policy, Permissions-Policy.
2. Restrinja o CORS das Edge Functions à(s) origem(ns) do app (produção + preview), lendo de env, em vez de `*`.
3. Adicione rate limiting básico às Edge Functions públicas/sensíveis (por IP/user), ex.: contador em tabela/KV com janela de tempo, ou Upstash Ratelimit.
4. Ajuste a CSP de Report-Only para enforce após validar que nada quebra no preview.

Critérios de aceite: headers presentes na resposta (verificar via curl/securityheaders.com); CORS rejeita origem desconhecida; chamadas acima do limite recebem 429.
Verificação: mostre os headers e um teste de rate limit.
Rollback: remover vercel.json / reverter cors.
